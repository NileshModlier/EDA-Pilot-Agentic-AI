# Example MCP Inspector session

This is the Phase P1.0 session for `gcd` on `sky130hd`. Start Inspector from the repository root after `ORFS_ROOT` is set. The same five calls are covered by `tests/test_run_flow.py::test_mcp_client_session`, which connects an MCP client to this server in process.

```powershell
cd "C:\Users\Administrator\EDA Pilot AI"
$env:ORFS_ROOT = "C:\path\to\OpenROAD-flow-scripts"
$env:EDA_PILOT_TIMEOUT_SECONDS = "7200"
$env:EDA_PILOT_MAX_RUNS = "8"
python -m pip install "mcp[cli]"
mcp dev eda_pilot/server.py
```

In Inspector, connect to server `eda-pilot-orfs`. Open the tools list. It contains `list_params`, `run_flow`, `get_metrics`, and `read_report`.

## 1. list_params

Call `list_params` with:

```json
{ "design": "gcd" }
```

`platform` defaults to `sky130hd`. The result's `source` is `configs/allowed_parameters.json` when the checkout has no `autotuner.json`, and `ORFS autotuner.json` when that file is present. A local autotuner file can only tighten bounds.

Representative rows:

| name | type | minimum | maximum | default | executable |
| --- | --- | --- | --- | --- | --- |
| `CORE_UTILIZATION` | int | 20 | 50 | 38 | true |
| `_SDC_CLK_PERIOD` | float | 0.8 | 5.0 | 1.1 | true |
| `CORE_ASPECT_RATIO` | float | 0.5 | 2.0 | 1.0 | true |
| `CTS_CLUSTER_SIZE` | int | 10 | 200 | null | true |
| `_FR_LAYER_ADJUST` | float | 0.1 | 0.3 | null | false |

The full result has 10 parameters. `executable: false` means `run_flow` will reject that name. A null default means the sky130hd/gcd config does not set the knob; omit it to keep the OpenROAD built-in.

## 2. run_flow

Call `run_flow` with a value inside the listed range:

```json
{
  "design": "gcd",
  "platform": "sky130hd",
  "params": { "CORE_UTILIZATION": 40 }
}
```

A successful finish returns:

```json
{
  "run_id": "8f1c0b1e2a3d4f5061728394a5b6c7d8",
  "status": "ok",
  "runtime": 912.4,
  "flow_variant": "p18f1c0b1e2a3d4f5061728394a5b6c7d8",
  "message": null
}
```

`run_id` is 32 hex characters generated by the server. `flow_variant` is `p1` plus that id. `runtime` is the wall-clock seconds. Copy `run_id` for the next two calls.

The server writes:

- `runs\<run_id>\stdout.log`
- `runs\<run_id>\stderr.log`
- `runs\<run_id>\manifest.json`
- `flow\reports\sky130hd\gcd\p1<run_id>\metadata.json` when ORFS reaches the metadata output

A real `gcd` finish often takes many minutes. At `EDA_PILOT_TIMEOUT_SECONDS` the status is `timeout` and the process tree is stopped.

## 3. get_metrics

Call `get_metrics` with the `run_id` from the finish:

```json
{ "run_id": "8f1c0b1e2a3d4f5061728394a5b6c7d8" }
```

The tool reads `reports\sky130hd\gcd\<flow_variant>\metadata.json` and maps ORFS keys such as `finish__timing__setup__ws` onto:

```json
{
  "run_id": "8f1c0b1e2a3d4f5061728394a5b6c7d8",
  "setup_wns": -0.012,
  "setup_tns": -0.04,
  "hold_wns": 0.005,
  "hold_tns": 0.0,
  "power": 0.00087,
  "area": 2145.3,
  "utilization": 37.5,
  "drc_count": 0,
  "runtime": 12.5,
  "missing": []
}
```

The numbers above are the shape of the JSON. A live ORFS run replaces them with that run's metadata. A missing key is `null` and its name is listed in `missing`. Nested metadata (`finish.timing.setup.ws`) is accepted as well as the flat `finish__timing__setup__ws` form.

## 4. read_report

Call `read_report` with the same run and the report name `timing`:

```json
{
  "run_id": "8f1c0b1e2a3d4f5061728394a5b6c7d8",
  "report_name": "timing"
}
```

The response contains the tail of the finish timing report, at most 200 lines:

```json
{
  "run_id": "8f1c0b1e2a3d4f5061728394a5b6c7d8",
  "report_name": "timing",
  "source_file": "6_finish.rpt",
  "line_count": 200,
  "truncated": true,
  "text": "...\nsetup slack -0.012\nhold slack 0.005"
}
```

`report_name` may also be `drc` or `congestion`. A filename, including `../6_finish.rpt`, is rejected:

```text
Error executing tool read_report: report error: report_name must be timing, drc, or congestion
```

## 5. Invalid parameter

Call `run_flow` with a utilization below the allowlist minimum:

```json
{
  "design": "gcd",
  "platform": "sky130hd",
  "params": { "CORE_UTILIZATION": 5 }
}
```

Inspector marks the tool call as an error. No make process starts. The message is:

```text
Error executing tool run_flow: validation error: CORE_UTILIZATION value 5 is outside [20, 50]
```

An unknown name fails the same way:

```text
Error executing tool run_flow: validation error: unknown parameter 'ABC_AREA'
```

`_FR_LAYER_ADJUST` fails because it is not executable. A string such as `40; rm -rf /` fails because the value must be an integer. None of those calls consume the run budget.
